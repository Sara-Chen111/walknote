# PRD：行记 WalkNote — 不赶场的旅行计划本（v0.1）

> 版本 v0.1.1 ｜ 2026-10-19 增补国内方向（高德双引擎与上海演示）｜ v0.1 骨架 2026-10-11 交付 ｜ 撰写：Sara ｜ 状态：骨架已交付并实测通过，待实地验收
> 一句话定位：**按每日步数预算排行程、把打卡动作写进计划的旅行工作台。**

---

## 1. 背景与问题

（详见《01-竞品调研报告》，此处只留结论）

- AI 行程规划已免费泛滥（圆周旅迹/指北旅行等"粘贴链接一键生成"），但**"赶场、忽略体力"是跨中美英的最高频差评**——用户做好的逐小时计划，一天实际只完成 2 个景点。
- **步数/体力预算是无人占据的一等约束**：专利有技术（CN112001538A 等）但无产品化；而慢节奏旅行趋势（2025 年 68%）与"带父母不敢排满"的焦虑正在放大需求。
- **打卡机位与行程零闭环**：蚂蚁摄影有机位无行程、规划 App 有行程无机位、小红书有机位内容但进不了计划。
- **中小红书收藏 = 信息坟墓**：800+ 条收藏实际可用不到 5%，手动拼 Excel 又无法感知点与点的距离。

## 2. 产品定位与差异化

| 维度 | 行记的选择 | 不做什么 |
|---|---|---|
| 核心用户 | 出片型自由行玩家 / 体力敏感出行 / 慢充 Citywalk 人群（v0.1 = Sara 自己的日本行） | 不服务"跟团打包"与机酒预订需求 |
| 核心价值 | **不赶场（步数预算）+ 出好片（打卡卡）+ 有产出（H5 手记）** | 不追求"一键生成全行程"（红海且被骂） |
| 人机关系 | 用户定约束、AI 出候选、**硬约束由代码校验**、每步可改 | 不做全自动不可编辑的"黑盒行程" |
| 数据策略 | 用户主动导入攻略（合规第一） | 不做小红书爬虫底座 |
| 商业模式 | 内容包 / 实体手账 / 导流（验证期后启用） | 不做纯工具订阅依赖（中文付费意愿低） |

**产品故事（对用户）**：你收藏的每篇攻略都会变成计划本里的一页——几点到、拍什么、走多少步，走得动才排得进去；回来一键出 H5 手记。
**产品故事（对面试官）**：AI 行程最大的差评是"赶场"，所有产品都在优化"生成"，我把"体力预算"做成了确定性校验闭环——LLM 只出候选，距离与步数由真实路网计算，超预算就地提示。

## 3. 目标用户与画像

**主画像（v0.1 即开发者本人，dogfooding）**：Sara——11 月赴日，攻略重度依赖小红书，在意出片，不愿赶场。验收标准就是"我自己敢拿它上路"。

**次画像（后续商业化对象）**：
- 出片型自由行玩家（会为机位排行程，出行前后发小红书）
- 体力敏感的家庭/带父母出行（最怕行程崩在体力上）
- 慢充 Citywalk 人群（1 万步档位 + 留白日）

## 4. 核心场景与用户故事（v0.1 范围）

**场景 A：导入攻略（内容入口）**
- A1. 作为用户，我能把小红书笔记正文/链接文字粘贴进采集箱，AI 解析出景点 + 打卡卡（机位/构图/姿势/时段/文案），我编辑确认后进入景点池。
- A2. 作为用户，我能上传攻略截图，视觉模型读图解析（攻略正文大量在图片里）。
- A3. 作为用户，我能手动添加景点（名称/区域/停留时长/坐标）作为兜底。
- A4. 同名景点重复加入时自动合并，不产生重复项。

**场景 B：按步数预算生成行程（核心闭环）**
- B1. 作为用户，我能设置往返日期、每日出发/收尾时间、住宿点、**每日步数档位（1 万/2 万/3 万步，逐日可改）**、**交通档次（纯步行/公交地铁+步行/打车为主）**。
- B2. 我能标注景点为必去（硬约束）或次选，一键生成逐日行程。
- B3. 每段路（含住宿↔首末站往返）都显示真实/估算步行距离与步数；当日累计步数对预算显示进度条。
- B4. 超预算时我得到明确提示（删点/改交通档/挪到留白日），并能手动上下移、增删景点，改动后即时重算。
- B5. 每段路我能一键跳转地图/换乘查询（Google Maps / Yahoo!乗換案内）核对。

**场景 C：行中执行（计划本）**
- C1. 一天一页：到点时间、地点、打卡卡（机位/构图/姿势/时段/文案）、停留时长一目了然。
- C2. 我能上传攻略参考图与自己的打卡照（本地压缩存储），拍完勾选「已打卡」。
- C3. 「今天」自动定位到当天页；全部数据本机存储，离线可用。

**场景 D：行后产出（展页）**
- D1. 我能一键让 AI 起草手记文案（引言 + 每日配文），并逐条修改。
- D2. 我能生成并预览 H5 手记：按天分页、照片墙、步数统计、**同款对比（攻略参考 vs 我的打卡）**。
- D3. 我能下载单文件 HTML（照片内嵌）用于分享。

**场景 E：模型与地图配置（BYOK）**
- E1. 我能配置 OpenAI 兼容 API（Endpoint/Key/文本模型/视觉模型），Key 仅存本机。
- E2. 我能配置高德 Web 服务 Key（境内）与 OpenRouteService Key（境外）启用真实路网；引擎按坐标自动选源（境内高德 + GCJ-02，境外 ORS + WGS-84），境内公交段取高德真实换乘数据；未配置的一侧明确显示「估算」。
- E3. 不配置任何 Key 时全流程可体验（演示模式）。

## 5. 功能范围

### v0.1（本迭代，11 月日本行前完成）
1. 攻略采集箱：粘贴解析 + 截图解析 + 手动添加 + 同名合并 + 导入记录
2. 规划台：行程卡（日期/住宿/默认档位）、景点池（必去/次选）、本地规则编排 + AI 编排（BYOK）、步数引擎（距离/分段/时间轴/预算校验）、逐日行程手动微调
3. 计划本：一天一页、打卡卡、参考图与打卡照上传、随手记、完成勾选
4. 展页：AI 手记文案、H5 生成/预览/下载
5. BYOK 设置（文本/视觉模型）+ 高德/ORS 双地图 Key + 数据导出备份；两套演示行程（上海 4 天 · 国内 / 东京 5 天 · 海外）

### v0.2（实地验证后）
- **国内方向**：高德 POI 搜索接入采集箱（俗称地名 → 坐标校准，严格缓存）；飞猪 FlyAI（景点/门票/酒店搜索 + `jumpUrl` 分佣，需极薄边缘代理）；携程/同程联盟 CPS 链接挂 POI 卡片
- 日本换乘 API 接入（Jorudan）、离线地图、行中"今天/明天"视图
- 照片 AI 配文与打卡点评（轻微多模态）+ 同款对比增强
- H5 在线链接分享、手记模板、多行程管理
- 攻略截图批量导入

### Non-goals（明确不做）
- 注册登录与云同步、机酒门票预订、多人协作、小程序与原生 App（行后再评估）、全球通用规划（先做日本）、自动爬取小红书、视频生成

## 6. 关键产品判断（面试叙事素材）

1. **体力是工程问题不是提示词问题**：不指望模型"考虑用户体力"，把它拆成确定性闭环——步幅换算（0.74m）、真实路网距离（ORS）、分段交通决策（按档位阈值）、住宿往返计入、超预算就地提示。LLM 只负责"哪几天去哪些点"。
2. **打卡卡是行程的一部分**：机位不是独立工具，而是绑定在景点上的执行清单——行中打开计划本即行动，行后自动进入 H5 的"同款对比"。
3. **留白日是功能不是空白**："不赶场"首先意味着允许什么都不做；演示行程第 5 天即留白日。
4. **合规是产品设计的一部分**：不做爬虫，把取数方式设计成"用户把攻略分享给 App"——既规避 490 万判赔级的法律风险，也形成"你的收藏不再进坟墓"的产品叙事。
5. **BYOK + 演示模式**：零推理成本验证（沿用墨流 InkFlow 工程基因），无 Key 也全流程可体验。
6. **H5 是唯一的增长引擎**：工具自然增长极慢（Tern 两年 $100 MRR），行后手记自带分享场景与品牌签名。

## 7. 技术方案（MVP）

- **架构**：Vite + React 单页应用（JSX，无 TS），手机优先响应式；纯前端零后端。
- **存储**：行程与配置存 localStorage；打卡照片/参考图本地压缩（≤1600px，JPEG）后存 IndexedDB，界面只持有缩略图；支持导出 JSON 备份。
- **AI 接入**：OpenAI 兼容协议（`/chat/completions`）直连，BYOK；结构化任务全部要求纯 JSON（`extractJSON` 容错解析），失败降级本地规则。
- **步数引擎**（`src/lib/geo.js`）：双引擎按坐标自动选源——境内高德 `v3/direction/walking`（GCJ-02）+ 公交段 `v3/direction/transit/integrated` 真实换乘，境外 ORS `foot-walking`（WGS-84），无 Key 时 haversine × 1.25 估算；`planLeg` 按交通档阈值分段（步行/换乘/打车，换乘档 1.5 km）；`annotateDay` 计算住宿↔景点↔景点全程步数与时间轴；`fallbackPlan` 本地规则编排（必去优先 + 按日轮转 + 就近排序）。
- **地图与换乘**：不内嵌地图 SDK（v0.1）；每段路深链高德 URI（境内，免 Key）/ Google Maps + Yahoo!乗換案内（境外），零成本零依赖。
- **H5 导出**（`src/lib/export.js`）：模板字符串生成单文件 HTML，照片 base64 内嵌，导出即分享。
- **开发方式**：AI 编程（vibe coding）全量承担编码，产品负责人做需求、验收与迭代决策。

## 9. 商业化设计（验证期后启用）

- **机位内容包**：按城市打包"打卡卡"（对标蚂蚁摄影付费心智，但绑定行程）
- **实体手账印刷**：H5 手记 → 实物（Polarsteps 模式已验证）
- **导流**：门票/周游券/eSIM 弱导流（不碰机酒闭环）
- **轻订阅**：多行程/云同步/多设备（最后考虑）

**测试中发现并修复的真实问题**：① 路段信息在手机宽度下换行错乱（改为"路线+类型一行、数据一行、链接右对齐"）；② 从采集箱子页点底栏「规划台」无法返回主页（子页面状态上提至 App）；③ 重复加入同名景点会产生重复项（改为合并补全）。

**未覆盖**：图片上传（浏览器工具不支持文件选择器）——计划本照片上传与截图解析入口需在真机上手测；控制台日志（工具未提供监听能力，全程无可见错误表现）。
