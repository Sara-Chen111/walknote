# 行记 WalkNote 产品总规划：不赶场的旅行计划本

> 版本 v0.2 ｜ 2026-10-19（v0.1 于 2026-10-11）｜ 状态：总规划定稿；10-19 增补国内方向与平台接入决策（见 3.2、8、9 节）
> 一句话：**按每日步数预算排行程、把打卡动作写进计划的旅行工作台——不赶场，出好片，行后一键生成 H5 旅行手记。**

---

## 0. 产品哲学（为什么做、为什么不一样）

**市场现状**：2025-2026 年所有旅行工具都在卷"AI 一键生成行程"——粘个链接、说句偏好，几十秒吐出一份计划。结果是幻觉（不存在的餐厅、已搬迁的市场）、过时信息、以及最高频的差评：**赶场**——用户做好的逐小时计划，一天实际只完成 2 个景点；"7 天瑞士行程 physically demanding"、"父母直接崩盘"。与此同时，把攻略变成照片的"打卡"环节，至今没有产品把它当作行程的一部分：机位工具（蚂蚁摄影）有机位无行程，规划工具（圆周旅迹/Wanderlog）有行程无机位，小红书有全网的机位内容但无法结构化进计划。

**行记的主张**：

1. **体力是行程的一等约束。** 行程规划的第一输入不是"想看什么"，而是"走不走得动"：每日步数预算（1 万/2 万/3 万步）由用户设定，每条路段的步行距离和步数被真实计算、逐段标注、超预算就地提示——而不是让模型拍脑袋估时间。
2. **打卡是计划的一部分，不是附赠。** 每个景点挂一张"打卡卡"（机位/构图/姿势/最佳时段/文案），来自用户自己导入的攻略内容，行中打开就是一页可执行的行动清单。
3. **行程的终点是一份手记。** 规划与打卡的产物天然会流动——行后一键生成 H5 旅行手记（含"攻略参考 vs 我的打卡"同款对比），这既是用户的情感回报，也是产品唯一的分享飞轮。

**产品口号**：不赶场，把攻略走成自己的照片。

**给面试官的叙事**：AI 行程规划最大的差评是"赶场"和"体力被忽略"，但所有产品都在优化"生成"，没人把"体力预算"做成硬约束。行记用"步数预算 + 真实路网距离 + 逐段校验闭环"把体力做进产品层（LLM 只生成候选，硬约束由确定性代码校验）；同时把小红书攻略里的打卡机位结构化绑定到每个景点，形成"攻略 → 计划 → 照片 → H5 手记"的完整闭环——三个环节在现有产品里各占其一，无人打通。

## 1. 用户与场景

**主用户（v0.1 = 自己，11 月日本行）**：Sara——出境自由行、攻略重度依赖小红书、在意"出片"、体力有限不想赶场。当前工作流痛点：小红书收藏夹是"信息坟墓"（收藏几百条，实际可用不到 5%）、手动拼 Excel 无法感知点与点的距离、AI 生成的行程不信任（幻觉 + 赶场）。

**目标用户画像（商业化验证对象）**：

| 画像 | 特征 | 为行记付费的理由 |
|---|---|---|
| 出片型自由行玩家 | 会为一个机位排半天行程，出行前后发小红书 | 机位内容包 / 无广告的干净工具 |
| 体力敏感的家庭/带父母出行 | 最怕"行程崩在体力上" | 步数预算 = 防翻车的确定性 |
| 慢充式 Citywalk 人群 | 2025 年 18-28 岁选慢节奏旅行比例已达 68% | 1 万步档位 + 留白日设计 |

```
│                                            │              │
│                                            ▼              │
│  ①规划台 ═══════════ 步数引擎（全系统的一等约束）★心脏        │

│                           │                               │
│                           ▼                               │

│                           │                               │

```

数据流主线：**攻略采集箱 → 规划台 → 计划本 → 展页**；「步数预算」贯穿四个环节，四处可查（规划超限提示 / 每页步数头 / H5 步数统计）。

| 板块 | 定位 | 一句话 |
|---|---|---|
| 攻略采集箱 | 内容入口层 | 把小红书攻略"分享"给行记，解析成景点 + 打卡卡 |
| ① 规划台 | 步数驱动的行程引擎 | 必去、次选、步数档位进去，不赶场的逐日行程出来 |
| ② 计划本 | 行中执行界面 | 一天一页：几点到哪、拍什么、拍完打勾 |
| ③ 展页 | 情感出口与分享飞轮 | 一键出 H5 手记，攻略参考与自己的照片并排 |

## 3. 各板块详细规划

### 3.1 攻略采集箱（内容入口层）

**定位**：解决"小红书收藏 = 信息坟墓"的问题。产品不做自动抓取，而是让用户**主动把攻略分享给 App**（粘贴笔记正文/链接文字、上传攻略截图），AI 解析成结构化内容，用户确认后进景点池。

**解析产物（每个景点）**：名称 / 区域 / 建议停留时长 / 为什么值得去 / **打卡卡**（机位、构图、姿势、最佳时段、文案）/ 注意事项 / 置信度。

**关键设计**：
- **人工确认强制环节**：小红书地名常是俗称（"XX 路口左转第 3 根柱子"），必须给用户编辑 + 确认的 UI，不自动入库
- 截图路径走视觉模型（轻微多模态）——攻略正文大量在图片里，这是 OCR 之外的必要能力
- 原文只在本机内存处理，不留存（合规要求，见 03 文档）

### 3.2 规划台（步数引擎）★ 系统心脏

**定位**：以"体力预算"为一等约束的行程编排器。不是"生成一份看起来合理的行程"，而是"生成一份**走得动**的行程"。

**输入**：
- 往返时间节点、每日出发/收尾时间
- 必去景点（硬约束）/ 次选景点（尽量安排）
- **每日步数档位**：1 万步·慢充 / 2 万步·标准 / 3 万步·特种兵（可逐日单独设置）
- **交通档次**：纯步行 / 公交地铁 + 步行 / 打车为主（决定超距离路段是走、是换乘、还是打车）
- 住宿点（参与步数计算与就近排序）

**步数引擎规格**（确定性计算，不靠模型估）：

| 环节 | 规则 |
|---|---|
| 步数换算 | 步幅 0.74 m（成人均值）：1 万步 ≈ 7.4 km；预算 = 步数 × 0.74 |
| 路段距离 | **双引擎按坐标自动选源**：境内走高德 Web 服务（个人认证免费 15 万次/月，GCJ-02），境外走 OpenRouteService（免费 2000 次/日，WGS-84）；都无 Key 时降级为直线距离 × 1.25，界面标注「估算」 |
| 计入范围 | **住宿 → 首站 → 各站 → 回住宿**全程（往返住宿的步行最容易被忽略） |
| 分段决策 | 距离 ≤ 交通档上限（步行档 2.5km / 换乘档 1.5km / 打车档 0.6km）→ 步行；超出 → 按档次换乘（含 500m 接驳）或打车 |
| 换乘估时 | 境内有高德 Key 时取**真实换乘数据**（接驳步行距离 + 乘车时长）；否则 ≈15 km/h 含候车换乘估算。行中可点「查换乘」跳高德（境内）/ Yahoo!乗換案内 + Google Maps（境外）核对 |
| 时间轴 | 出发时间 + 各站停留 + 各段行程时间顺推，超出每日收尾线即提示 |
| 校验闭环 | LLM 只生成"哪几天去哪些点"的候选编排 → 代码算真实步数 → 超预算就地提示（删点/改交通档/挪到留白日），支持手动上下移与增删后即时重算 |

**留白日是设计，不是空白**：允许某天不排任何点（v0.1 演示行程第 5 天即留白日）——"不赶场"首先意味着允许什么都不做。

### 3.3 计划本（一天一页）

**定位**：行中的执行界面。以"天"为单位的物理隐喻：一天一页。

**每页内容**：日期与当日步数头（预算进度条）→ 时间轴（到点时间 + 地点 + 停留时长）→ **打卡卡**（机位/构图/姿势/时段/文案）→ 攻略参考图上传（用于同款对比）→ 打卡照片（可多张）→ 随手记 → 「已打卡」勾选。

**行中特性**：数据全部本机存储（离线可用）；「今天」自动定位到当天页；照片本地压缩后存 IndexedDB，不占网络。

### 3.4 展页（H5 旅行手记）

**定位**：行程的情感出口 + 产品的分享飞轮。行后一键把计划本变成一份可发出去的 H5 手记。

**内容**：封面（标题/日期/统计：天数、地点数、总步数、照片数）→ 引言 → 按天分页（当天配文 + 时间轴 + 打卡卡节选 + 照片墙 + **同款对比**：攻略参考图与自己的打卡照并排）→ 页脚签名。

**交付形态（v0.1）**：单文件 HTML（照片 base64 内嵌），下载后发文件即分享；v0.2 起支持在线链接。

**文案**：AI 起草（引言 + 每日配文，手记语气，禁止"必去/打卡圣地"式攻略话术），用户可逐条修改。

## 4. AI 角色编制

| AI 角色 | 驻扎板块 | 职责 | 输入 → 输出 | 核心护栏 |
|---|---|---|---|---|
| 攻略解析员 | 采集箱 | 从攻略原文/截图中提取景点与打卡卡 | 攻略文本/截图 → 结构化 JSON | 不编造景点；低置信度标注；人工确认才入库 |
| 行程编排员 | 规划台 | 生成"哪几天去哪些点"的候选编排 | 景点池 + 约束 → 逐日候选 | **只出候选，不碰步数**——距离与预算由代码校验 |
| 打卡点评员 | 计划本 | 行中点评打卡照（与攻略建议的差距） | 照片 + 打卡卡 → 3-5 句点评 | 不打分、不长篇大论（轻微多模态） |
| 手记撰写员 | 展页 | 起草 H5 手记文案 | 行程纪要 → 引言 + 分日配文 | 手记语气，不许出现攻略话术 |

工程原则：**结构化任务一律要求纯 JSON（失败有兜底），硬约束（步数/时间）永不交给模型**。全部能力走 OpenAI 兼容协议，BYOK；无 Key 全链路降级演示模式（本地规则编排 + 内置示例），保证产品流程完整可体验。

## 7. 验证假设

| 编号 | 假设 | 验证方式 | Go 标准 |
|---|---|---|---|
| H1 | "步数预算"是真实需求而非自嗨 | 自用 + 行后复盘：预算是否影响了行程决策 | 至少 3 天因预算提示调整了原计划 |
| H2 | 打卡卡能提高"出片率"与满意度 | 行后统计：按打卡卡拍摄的照片占比 | ≥ 50% 的打卡照参考了卡片建议 |
| H3 | H5 手记有自发传播性 | 行后发出后观察：朋友询问"用什么做的" | ≥ 3 人主动询问 |
| H4 | 用户愿为机位内容/工具付费 | 后续 mini 测试（小红书内容包/付费模板） | 有真实付费或强意向信号 |

若 H1/H2 被推翻（自己用下来发现步数约束并不重要），诚实复盘并调整定位——这本身是作品集里"产品判断"的素材。

## 8. 商业化与作品集叙事（方向）

**切入点（2026-10-19 更新为双线）**：
- **自用验收线**：11 月日本行（ORS 路网 + 深链换乘），验证产品闭环与 H1-H3 假设
- **商业化主线：国内城市游**（上海/成都/重庆/西安等 Citywalk 热点城市）。理由：① 高德提供个人可用、浏览器可直连的真实路网与公交换乘数据，步数预算的可信度在国内远高于海外；② 飞猪 FlyAI 是唯一官方面向个人 Agent 开放的国内 OTA，景点/门票/酒店搜索 + 直订链接 + 分佣一次打通；③ 国内慢节奏旅行趋势（2025 年 18-28 岁选慢节奏比例 68%）与小红书攻略密度都在国内更高
- 不做"全球通用规划器"——通用场景会被携程/高德的免费 AI 行程碾压，个人 MVP 不正面打

**变现候选（M3 后验证）**：
- **飞猪 FlyAI 分佣**：景点/门票/酒店搜索结果直接挂 `jumpUrl`，酒店与度假类成交自动归因佣金（官方面向个人推广者，比例待控制台核实）；携程联盟 / 同程联盟 refid 链接作为补位（门票 2%-4%）
- **机位内容包**：按城市打包的"打卡卡"（机位/构图/时段），对标蚂蚁摄影的付费心智，但绑定在行程里
- **实体手账印刷**：把 H5 手记变成实物（Polarsteps 模式，10M 用户/$10M+ 收入验证过"情感物"的付费意愿）
- **轻订阅**：多行程管理、云同步、多设备（国内对纯工具订阅意愿低，放最后）

**明确不做**：不做"粘贴链接一键生成路线"（已被圆周旅迹等免费做烂）、不做机酒预订闭环、不做通用攻略社区、**不接美团**（官方对个人开发者关闭且无 POI API，餐厅 POI 用高德代替）。

**作品集叙事**："不赶场的旅行计划本：用『步数预算 + 真实路网距离 + 校验闭环』把 AI 行程最被诟病的『赶场』做成了产品级硬约束；把小红书攻略里的打卡机位结构化绑定到行程，形成攻略→计划→照片→H5 手记的闭环；行后产物自带分享飞轮。"

## 9. 风险与开放问题

| 风险 | 应对 |
|---|---|
| 3 周内做不完（11 月行前） | v0.1 只服务日本行，一切非必需砍掉；骨架已先跑通验证风险 |
| 攻略解析质量（俗称地名匹配） | 人工确认强制环节 + 可手动添加兜底；v0.2 接地图 POI 模糊匹配 |
| 小红书数据合规 | 只走"用户主动导入"；不自动抓取、不留存原文（详见 03 文档） |
| 步数可信度依赖地图 Key | 境内高德 / 境外 ORS 双引擎，提供直线估算降级并明确标注；行中可点深链用高德 / Google Maps 核对 |
| 地图个人配额为「学习研究用途」，正式商用需企业许可（5 万/年起） | MVP 期按个人配额跑；商业化前注册公司走高德乘风计划（初创免费 1 年）；高德是唯一允许个人付费加量的平台，突发用量可兜底 |
| 飞猪 FlyAI 浏览器不可直连（CORS 白名单 + 签名） | v0.2 加一个极薄边缘代理（Cloudflare Worker）转发；接受「零后端」变为「近零后端」 |
| 高德 POI 搜索配额仅 5,000 次/月 | 只用于采集箱的"俗称地名 → 坐标"校准；本地缓存 + 节流；不做高频搜索 |
| 中文工具付费意愿低 | 变现优先"内容包/实物/导流"而非纯订阅 |
| 「行记」名字较拥挤（迹遇、云履行记等） | 无同名冲突；作品集阶段可接受，商业注册前再做商标检索 |
